## 2. 구조

칸과 유닛이 같은 정의에서 나온다. `scripts/vica_terminator_layout.py` 의 `Term` 에 `unit`
필드를 더하고, `--units --stage <단계>` 로 유닛만 만든다. 칸의 rc 는 쓰지 않는다 —
`t_llm_local.rc` 는 10-24 에 손으로 고친 판이라 다시 쓰면 사라진다. 리팩터 전후 rc 34칸이
같음을 대조했다.

```
vica-can.service (system)      can1 장치가 나타나면 한 번. 링크를 내리지 않는다
vica-base.target (user)        Wants: 아래 10개
  1a  display · lidar · app · web · supervisor
  1b  container → d455 · imu
  1c  safety → motor            Restart=no
```

- 유닛은 `run_<칸>.sh` 를 실행한다. 칸과 같은 환경 블록(ROS·지도·덧씌움)에
  `~/.bashrc` 가 주던 값(CUDA 경로·로캘)을 직접 더했다.
- 끝나는 값: 0 정지 신호를 받음 · 70 스스로 끝남 · 75 이미 떠 있어 거부
  (`RestartPreventExitStatus=75`).
- 정지는 `KillMode=control-group` + SIGINT. 칸의 Ctrl+C 와 같다.
- 유닛끼리는 `After=` 만 건다. `Requires`·`BindsTo` 는 쓰지 않는다 — motor 재기동이 다른
  유닛으로 번지면 안 된다(09-07 모터 재기동이 controller_server 를 죽인 전례).
- 순서는 `ExecStartPre=vica_wait.sh` 가 지킨다. safety 는 `can1` 이 생긴 뒤
  (`emergency_stop_node` 가 CAN 소켓을 기동 때 한 번만 연다), motor 는 `can1` UP 과
  `safety_supervis` 프로세스 뒤.

## 4. 실기에서만 나온 것

단위 시험은 통과했는데 띄워 보고서야 드러난 것들이다. 전부 시험을 더하고 고쳤다.

1. **빈 `map_yaml` 이 상태 노드를 죽인다.** `supervisor_bringup.launch.py` 설명에는 "비우면
   자동 감지"라고 적혀 있는데, 비우면 `-p map_yaml:=` 가 넘어가 rcl 이 해석하지 못한다.
   launch 는 살아 있어 유닛은 active 로 보였다. 유닛은 칸처럼 `map_yaml` 을 넘기게 되돌렸고,
   launch 는 값을 따옴표로 감싸게 고쳤다(앱 9ab04ac — 실행본에는 아직 없다).
2. **rosbridge 는 프로세스 이름이 `python3` 다**(`#!/usr/bin/env python3`). `pgrep -x
   rosbridge_webso` 는 못 찾는다. 유닛에는 명령줄로 찾는 검사를 넣었다. **⑪ app 칸의 guard 는
   같은 이유로 지금도 걸리지 않는다** — 칸 쪽 수정은 rc 재생성이 필요해 남겨 두었다.
3. **명령줄 패턴은 `^` 로 맨 앞에 묶어야 한다.** 안 묶으면 그 글자를 담은 아무 셸이나 걸린다.
   확인용 명령이 rosbridge 로 오인돼 유닛이 기동을 거부했다.
4. **도는 스크립트를 제자리에서 덮어쓰면 안 된다.** bash 는 스크립트를 실행하면서 읽는다.
   유닛이 도는 중에 `run_*.sh` 를 다시 쓰자, 돌던 쪽이 바뀐 파일을 이어 읽어 문법 오류를
   냈고 한 유닛은 정지 도중 launch 를 한 번 더 실행했다. 새 파일을 만들어 바꿔 끼운다.
5. **`run_d455_cloud.sh` 의 launch 는 SIGINT 를 무시한다.** launch 를 `&` 로 띄우는데,
   터미널 없는 bash 는 그런 프로세스의 SIGINT 를 무시로 둔다(`SigIgn` 비트 0x2 확인).
   launch 에만 보내면 13 s 무반응이고, SIGTERM 으로 올리면 launch 만 죽어 노드가 고아로
   남는다. 노드는 SIGINT 를 잡아 4 s 에 내려가므로 정지 신호를 노드에도 보낸다. 칸에서는
   Ctrl+C 가 노드에도 직접 가서 드러나지 않던 문제다. ⑮ detector 를 유닛으로 만들 때도 같은
   함정이 있다.
6. **웹 앱은 처음 여는 주소에서 `ws://127.0.0.1:9090` 으로 붙는다.** 다른 기기에서
   `http://<젯슨 IP>:5000` 을 열면 "ROS2 연결 안 됨" 이 뜬다. 설정에서 `ws://<젯슨 IP>:9090`
   과 `http://<젯슨 IP>:8000` 으로 바꾼다.
7. `journalctl --user -u` 는 저널 보존을 켜기 전에는 비어 나온다. `--user-unit=` 을 쓴다.

## 5. 2a 주행 묶음 실기 (14:31~14:51, 바퀴 띄움)

`systemctl --user start vica-drive.target` 으로 nav2·posecheck·mission·handle·monitor 를 띄웠다.

| 확인 | 결과 |

| 내리고 올리기 3회 | 정지 5~10 s · 전부 `Result=success` · 남은 프로세스 0 · 중복 0 |
| 기본 묶음 | motor·safety pid 그대로. 모터 출력 내내 0 |
| 활성 | 14:50:50 앱 초기 위치(pose_bootstrap 점수 70.9) → 14:50:54 `Managed nodes are active` |
| 활성 뒤 | Nav2·미션 오류 0, supervisor 전이 0, 세그폴트 0 |

발견한 것:

1. **Nav2 를 내릴 때 supervisor 유령 정지(3번 중 1번).** Nav2 프로세스 20여 개가 한꺼번에 내려가는
   순간(14:36:21) `emergency_stop_node` 가 2.17 s 멈췄다. `/emergency_stop` 하트비트가 2.0 s
   (`estop_timeout_sec`)를 넘어 supervisor 가 `READY_TO_GO -> FAULT -> ESTOP_RELEASED_WAIT_RESET`.
   래치 원인이 없어 자동 복구가 붙지 않는다. 칸 시절 로그에도 같은 문구가 153줄 있다(원인이 Nav2 정지였는지는
   미확인). 앱의 주행→지도 전환이 Nav2 를 내리므로 2b 전에 정해야 한다. safety 변경이라 승인 대상.
2. **controller_server bond 4 s 실패로 Nav2 기동 중단(4번 중 1번).** `Server controller_server was
   unable to be reached after 4.00s by bond`. 같은 시각 EKF 주기 미달, load 16~24 — 연속 재기동과
   다른 세션의 빌드·분석이 겹쳤다. 칸 시절 903번 중 4번. bond 시간이 1.3·5.9·2.5·0.4 s 로 시한에
   가깝다. `systemctl --user restart vica-nav2` 만으로 복구(미션은 그대로). 주행 묶음 유닛들이 Nav2
   configure 와 동시에 떠서 부하를 더하는지는 미확인.
3. **미션 칸의 guard `vica_mission_ma` 는 실제 이름(`mission_manager`)과 달라 걸리지 않는다.** 유닛은
   실제 이름을 더했다(2cdeccc). 칸은 rc 재생성이 필요해 그대로.
4. collision_monitor 의 `Failed to bring up all requested nodes` 는 launch 의 12초 재시도가 이미
   active 인 노드에 거는 기존 동작이다(지난 기동 40번 중 39번). 무시해도 된다.

## 6. 미검증

- 버튼을 푼 부팅 반복. 1회만 봤다. 부팅 부하로 `/emergency_stop` 하트비트가 2 s 넘게 늦으면
  supervisor 만 `WAIT_RESET` 에 남을 수 있다(코드상 가능, 관측 안 됨).
- 버튼을 누른 채 **부팅**. 유닛을 손으로 띄운 경우만 봤다.

- 원격 화면이 끊겨도 노드가 출력 쓰기에서 멈추지 않는지(10-30·11-07 사고 재현).
- 와이파이 없이 부팅했을 때 docker·컨테이너.
- 드라이버 전원 투입 때 `can1` 상태에 따른 바퀴 거동(매뉴얼 기록 상충). 이번 작업과 무관하게
