## 2. 원인 — 67 ms 응답을 50 ms 확인 시각으로 나눴다

- 모터 노드 C++ 판(`motor_core.hpp:221-222`, `504-506`)은 30 Hz 타이머로 깨되 "속도가 바뀌었거나 지난 전송 뒤 50 ms 지났을 때"만 보낸다. 일정 속도에서는 두 번에 한 번 = 67 ms, 가속 중에는 매번 = 33 ms. 드라이버는 명령마다 C5 위치를 돌려준다.
- `encoder_feedback.py` 는 50 ms 타이머마다 CAN 을 비우고, 새 좌우 쌍이 있으면 **타이머가 돈 시각**으로 `vx = 이동 ÷ dt` 를 냈다. 67 ms 짜리 이동이 50 ms 칸(1.34 배)과 100 ms 칸(0.67 배)으로 나뉘고, 짧은 칸이 두 배 많다.
- 이상적인 예: 200 ms 동안 6 cm(0.30 m/s). 적힌 속도 0.40·0.40·0.20 → 평균 0.33(11 % 빠름). 총거리 ÷ 총시간은 맞지만 EKF 는 표본 평균을 먹는다.
- **CAN 기록으로 확정**: run92·93 의 `candump`(`~/vica_data/bags/101{2,3}_run9{2,3}_…_can1.log`)로 노드 동작을 그대로 흉내 내면 지금 방식 1.050~1.059(run92 bag 실측 1.054 와 일치), 프레임 수신 시각으로 나누면 0.996~1.004.

## 3. 결정 — AMCL 이 아니라 바퀴 쪽

사용자 질문: "wheel/odom 을 튜닝하는 게 맞는지, AMCL 오차 보정을 더 강하게 하는 게 맞는지."

- 늘 한쪽으로 쏠리는 오차는 AMCL 운동 모델 잡음(`alpha`, 0 중심 흔들림 가정)이 못 지운다. `alpha1` 0.4 는 08-13 실기에서 "주춤거림·머뭇거림"으로 이미 닫혔다.
- 다른 "세게" 손잡이(`update_min` 0.10, `max_beams` 180)는 이미 들어가 있다. `sigma_hit`↓·`z_rand`↓ 는 보정을 뚝뚝 튀게 하고 그 튐이 손잡이로 간다. CPU 도 90 % 근처라 여유가 없다.
- AMCL 은 지도 위 위치만 고친다. local costmap(`global_frame: odom`), 곧게 가기 같은 거리 동작, 회전 안내(`user_guidance.yaml` `odom_topic: /odom`), 매핑은 `/odom` 을 직접 쓴다.
- 앞뒤가 똑같은 복도에서는 AMCL 이 앞뒤를 못 잡아 10 % 가 그대로 위치 오차가 된다 `[미검증 — 추정]`.
- 바퀴 반지름 튜닝도 아니다. 부풀림이 속도 모양에 따라 변해 상수로 못 맞추고, 바퀴 셈 자체는 08-01 줄자로 ±1 % 였다.

## 4. 수리 (`f425116`)

- `encoder_feedback.py`: `read_can_frames()` 가 C5 위치와 함께 `msg.timestamp`(python-can 4.6.1, 커널 `SO_TIMESTAMPNS` 수신 시각)를 바퀴별로 저장. `loop()` 는 쌍의 시각 = 두 프레임 중 늦은 쪽, `dt` = 이번 쌍 − 지난 쌍, `header.stamp` 도 그 시각(앞으로만 가게).
- `pick_dt(frame_t, prev_frame_t, timer_dt)`: 시각이 없거나 역행·0.5 s 넘는 공백이면 타이머 시각으로 대체하고 경고 한 번.

- 시험: `test_encoder_math.py` 에 4개 추가(67 ms 응답 / 50 ms 타이머 재현: 예전 > 1.03, 새 1.00 ± 0.01, 대체 동작). `colcon test` 10 통과(저작권 1 건너뜀).
- `header.stamp` 가 최대 50 ms 앞당겨진다. 끊김 감시는 빈도(min_hz 5)로 판정해 영향 없다(`vica_system_monitor/config/probes.yaml` 189~197행).
